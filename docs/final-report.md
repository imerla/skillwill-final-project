# საბოლოო ანგარიში — FE-010

## 6. შედეგები — FE-010

### 6.1. წარმადობის მეტრიკების შედარება
პროექტის ოპტიმიზაციის შედეგების შესაფასებლად ჩატარდა Lighthouse-ის გაზომვები Mobile რეჟიმში. შედარებისთვის გამოყენებულია ოპტიმიზაციამდე და ოპტიმიზაციის შემდეგ მიღებული შედეგები.
| მეტრიკა | Before | After | ცვლილება |
|---|---|---|---|
| Performance | 48–55 | 91–96 | +41–48 ქულა |
| Accessibility | 87–94 | 92–96 | +2–9 ქულა |
| JavaScript ბანდლი (gzip) | 169.86 KB | 65.70 KB | შემცირდა 104.16 KB-ით (დაახლოებით 61%) |
| LCP | 4.1–5.8 წამი | 2.4–2.5 წამი | შემცირდა 1.6–3.3 წამით |
| CLS | 0.755–0.853 | 0–0.1 | მნიშვნელოვნად გაუმჯობესდა |
| TBT | 210–270 ms | 10–50 ms | შემცირდა 190–220 ms-ით |

### 6.2. შესრულებული ოპტიმიზაციები
პროექტის წარმადობის გასაუმჯობესებლად განხორციელდა შემდეგი ტექნიკური ცვლილებები:
- Layout Shift-ის შემცირება: სურათებისა და შესაბამისი კონტეინერებისთვის გამოყენებულია aspect-ratio და contain-intrinsic-size, რაც ხელს უწყობს გვერდის განლაგების სტაბილურობას კონტენტის ჩატვირთვისას.
- სურათების ჩატვირთვის ოპტიმიზაცია: ეკრანს ქვემოთ განთავსებული სურათებისთვის გამოყენებულია loading="lazy", რაც ამცირებს საწყისი ჩატვირთვისას მოთხოვნილი რესურსების რაოდენობას.
- მთავარი სურათის ჩატვირთვა: HeroBanner-ის მთავარი სურათი არ იყენებს Lazy Loading-ს, რათა მისი ჩატვირთვა საჭირო მომენტში არ გადაიდოს.
- სურათების გამოსახულება: object-fit: contain უზრუნველყოფს სურათების პროპორციების შენარჩუნებას და მათ სწორად ჩვენებას.
- Code Splitting: React-ის lazy და Suspense მექანიზმებით გვერდების კოდი დაყოფილია ცალკეულ დინამიკურ მოდულებად.
- Vendor Chunking: Vite-ის manualChunks კონფიგურაციით ბიბლიოთეკების კოდი ცალკეულ chunk-ებად არის დაყოფილი, რაც ხელს უწყობს საწყისი JavaScript ბანდლის ოპტიმიზაციას.
- კონტენტის რენდერის ოპტიმიზაცია: კატალოგის გრიდში გამოყენებულია content-visibility: auto და contain-intrinsic-size, რაც ეკრანს მიღმა არსებული კონტენტის რენდერის ოპტიმიზაციას და განლაგების სტაბილურობას უწყობს ხელს.

### 6.3. ქეშირებისა და სურათების შეზღუდვები
სერვერული მონაცემების ქეშირებისა და მართვისთვის გამოყენებულია TanStack Query. გლობალურად განსაზღვრულია 5-წუთიანი `staleTime`, ხოლო კონკრეტული query-ებისთვის შესაძლებელია განსხვავებული დროის განსაზღვრა.

სურათების ოპტიმიზაციის პროცესში გამოვლინდა API-ის შეზღუდვა: პროდუქტის სურათები ბრუნდება ფიქსირებული ზომით — 700×700 პიქსელი, JPEG ფორმატში.

Frontend-ის მხარეს გამოყენებული Lazy Loading ამცირებს საწყის ეტაპზე ჩატვირთული სურათების რაოდენობას, ხოლო განლაგების სტაბილიზაციის მექანიზმები ამცირებს Layout Shift-ს. თუმცა ეს მეთოდები თავად სურათის ფაილის ზომას არ ამცირებს.

ამ შეზღუდვის სრულად გადასაჭრელად საჭიროა API-ის მხარეს სხვადასხვა ზომისა და ფორმატის სურათების გენერაცია ან Image CDN-ის გამოყენება.

### 6.4. შედეგების შეფასება
ოპტიმიზაციის შემდეგ სამივე შემოწმებულ გვერდზე Performance მაჩვენებელი გადააჭარბებს დავალებით განსაზღვრულ მინიმუმს — 85 ქულას. Accessibility მაჩვენებელი გადააჭარბებს მოთხოვნილ 90 ქულას.

JavaScript ბანდლის ზომა შემცირდა 169.86 KB-დან 65.70 KB-მდე, რაც დაახლოებით 61%-იან შემცირებას წარმოადგენს. გაუმჯობესდა LCP, CLS და TBT მაჩვენებლებიც.

შედეგების მიხედვით, FE-010 დავალების ძირითადი წარმადობის მიზნები შესრულებულია. დარჩენილ შეზღუდვად რჩება API-ის მიერ სურათების მხოლოდ ერთი ზომით მიწოდება. ამ პრობლემის სრულად გადასაჭრელად საჭიროა Backend-ის ან გარე Image CDN-ის მხარდაჭერა.
