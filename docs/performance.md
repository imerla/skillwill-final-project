# წარმადობის ანგარიში — FE-010

## 1. გაზომვის პირობები
- დეპლოიმენტის URL: https://skillwill-final-project-eight.vercel.app/
- გაზომვის ინსტრუმენტი: Lighthouse 13.5.0
- რეჟიმი: Mobile
- ბრაუზერი: Incognito
- გაზომვების რაოდენობა: 3 გაშვება; ანგარიშში გამოყენებულია მედიანური შედეგები
- API: გაზომვების დროს API სერვერი მუშაობდა ნორმალურ რეჟიმში.

გაზომვები ჩატარდა production გარემოში, რათა შედეგები რეალურ მომხმარებლის გამოცდილებასთან მაქსიმალურად მიახლოებული ყოფილიყო. Before და After გაზომვებისას გამოყენებული იყო ერთი და იგივე პროექტი და შესაბამისი გვერდები.

## 3. შესრულებული ოპტიმიზაციები
პროექტის წარმადობის გასაუმჯობესებლად განხორციელდა შემდეგი ცვლილებები:

| № | შესრულებული ცვლილება | ტექნიკური მიზანი / შედეგი |
|---|---|---|
| 1 | სურათებისა და შესაბამისი კონტეინერებისთვის aspect-ratio და contain-intrinsic-size თვისებების გამოყენება | ელემენტებისთვის სივრცის წინასწარ განსაზღვრა და Layout Shift-ის შემცირება |
| 2 | loading="lazy" მექანიზმის გამოყენება ეკრანს ქვემოთ განთავსებული სურათებისთვის | საწყისი ჩატვირთვისას არასაჭირო სურათების მოთხოვნების შემცირება |
| 3 | სურათებისთვის object-fit: contain სტილის გამოყენება | სურათების პროპორციების შენარჩუნება და მათი სწორად ჩვენება |
| 4 | გვერდების დონეზე Code Splitting-ის განხორციელება React.lazy და Suspense მექანიზმებით | გვერდების კოდის ცალკეულ დინამიკურ მოდულებად დაყოფა და საჭიროების მიხედვით ჩატვირთვა |
| 5 | ბიბლიოთეკების ცალკეულ Vendor Chunk-ებად დაყოფა Vite-ის manualChunks კონფიგურაციით | JavaScript კოდის დაყოფა და საწყისი ჩატვირთვისას ჩამოსატვირთი კოდის მოცულობის შემცირება |

სურათების Lazy Loading გამოყენებულია ეკრანს ქვემოთ განთავსებული სურათებისთვის. მთავარი HeroBanner-ის სურათი არ იყენებს Lazy Loading-ს, რის შედეგადაც მისი ჩატვირთვა ამ მექანიზმის გამო არ გადაიდება. ეს მნიშვნელოვანია მთავარი ვიზუალური კონტენტის დროულად გამოსაჩენად და LCP მაჩვენებლის გასაუმჯობესებლად.

Code Splitting-ის შედეგად ავტორიზაციის, პროდუქტის დეტალების, კალათის, შეკვეთის გაფორმების, შეკვეთებისა და პროფილის გვერდების კოდი ცალკეულ დინამიკურ მოდულებად იტვირთება. შესაბამისად, მომხმარებელს ყველა გვერდის JavaScript კოდის საწყის ეტაპზე ჩამოტვირთვა აღარ სჭირდება.

## 6. შეზღუდვები და გადაუჭრელი საკითხები
ოპტიმიზაციის პროცესში გამოვლინდა API-ის მხრიდან სურათების მიწოდების შეზღუდვა. API პროდუქტის სურათებს აბრუნებს ფიქსირებული ზომით — 700×700 JPEG ფორმატში. ამ ეტაპზე API არ გვთავაზობს სხვადასხვა ზომის ან ფორმატის ვარიანტებს.

Frontend-ის მხარეს გამოყენებულია Lazy Loading და განლაგების სტაბილიზაციის მექანიზმები, თუმცა ეს მეთოდები თავად სურათის ფაილის მოცულობას არ ამცირებს.

სწორი გრძელვადიანი გადაწყვეტა იქნებოდა API-ის მხარეს სურათების სხვადასხვა ზომის გენერაცია ან Image CDN-ის გამოყენება, რაც საშუალებას მოგვცემდა კონკრეტული ეკრანის ზომის შესაბამისი სურათი ჩაგვეტვირთა.

## 7. დასკვნა
ოპტიმიზაციის შედეგად პროექტის წარმადობა მნიშვნელოვნად გაუმჯობესდა. Lighthouse-ის Performance მაჩვენებელი სამივე შემოწმებულ გვერდზე 85 ქულაზე მეტია, ხოლო Accessibility მაჩვენებელი 90 ქულას აღემატება.

JavaScript ბანდლის ზომა შემცირდა დაახლოებით 61%-ით, რამაც შეამცირა საწყისი ჩატვირთვისას ჩამოსატვირთი JavaScript კოდის მოცულობა. ასევე გაუმჯობესდა LCP, CLS და TBT მაჩვენებლები.

ყველაზე მნიშვნელოვანი ტექნიკური ცვლილებები იყო გვერდების დონეზე Code Splitting, vendor chunk-ების გამოყოფა და სურათების განლაგების სტაბილიზაცია.

API-ის სურათების ზომის შეზღუდვა დარჩა გადაუჭრელ საკითხად, რადგან მისი სრულად გამოსწორება Backend-ის ან გარე Image CDN-ის მხარდაჭერას მოითხოვს.

გაზომვების დამადასტურებელი Lighthouse-ის სქრინშოტები შენახულია docs/performance/ დირექტორიაში.
