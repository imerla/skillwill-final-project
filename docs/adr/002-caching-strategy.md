# ADR-002: ქეშირების სტრატეგია

## სტატუსი
მისაღებია

## კონტექსტი
აპლიკაცია იყენებს TanStack Query-ს სერვერიდან მონაცემების მართვისთვის. ქეშირების სტრატეგია არ არის განსაზღვრული და შეიძლება მოხდეს მომხმარებლის სხვა მონაცემების ჩვენება გადასვლის შემდეგ.

## პრობლემა
უსაფრთხოების საკითხველი: მომხმარებელმა არ უნდა იხილოს სხვა მომხმარებლის კალათა ან პროფილის ინფორმაცია გადასვლის შემდეგ.

## გადაწყვეტა
გამოვიყენეთ TanStack Query-ს ქეშირების სტრატეგია:

1. **ხანგრძლივი ქეში** (categories, filters): დიდი `staleTime` (წუთები/სააათები)
2. **მოკლე ქეში** (products, cart): მოკლე `staleTime` (წუთები)
3. **პერსონალური მონაცემები** (profile, orders): ყოველი გადასვლისას - cache-ის გასუფთავება
4. **კალათა**: ყოველი ცვლილების შემდეგ - invalidate, მაგრამ ავტომატურად უბრუნდება სერვერიდან

## ალტერნატივები
1. **localStorage cache:** ქეშირების მუდმივი შენახვა localStorage-ში
2. **Service Worker:** Cache-ის მართვა Service Worker-ით
3. **SWR (Stale-While-Revalidate):** ყოველი მოთხოვნისას ფონის ქეშის განახლება

## მიზეზები არჩეული გადაწყვეტისთვის
- localStorage-ს აქვს ზომის ლიმიტი (5-10MB)
- Service Worker დამატებით სირთულეს მოითხოვს
- SWR ზრდის სერვერზე დატვირთვას

## შედეგები
- უსაფრთხოება დაცულია - მომხმარებლის გადასვლისას ქეში გასუფთავდება
- ქეშირების მართვა ადვილი და მარტივია
- სერვერის დატვირთვა შემცირდება ხანგრძლივი ქეშის გამო
